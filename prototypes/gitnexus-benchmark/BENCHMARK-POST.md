# Benchmark Session: POST (With GitNexus)

## Setup — restore GitNexus before starting this session

Run these steps **before opening Claude Code** for the post session:

### 1. Restore `.mcp.json`
```json
{
  "mcpServers": {
    "design-tokens": {
      "command": "node",
      "args": ["shared/mcp-cli/dist/cli.js", "start", "design-tokens"]
    },
    "gitnexus": {
      "command": "npx",
      "args": ["gitnexus", "mcp"]
    }
  }
}
```

### 2. Restore `.claude/settings.local.json`
```json
{
  "enabledMcpjsonServers": [
    "design-tokens",
    "gitnexus"
  ],
  "enableAllProjectMcpServers": true
}
```

### 3. Rebuild the index and restore CLAUDE.md, AGENTS.md blocks, and skill files
```bash
npx gitnexus analyze
```
This rebuilds the knowledge graph index (`.gitnexus/`), re-appends the `<!-- gitnexus:start -->` block to both files, and regenerates `.claude/skills/gitnexus/`. Takes ~10 seconds.

### 4. Verify before opening the session
You should see:
- `gitnexus` in `.mcp.json` ✓
- `gitnexus` in `enabledMcpjsonServers` ✓
- `CLAUDE.md` ends with `<!-- gitnexus:end -->` ✓
- `.claude/skills/gitnexus/` exists (regenerated by analyze) ✓

## Your role in this session

You are running the **"after" half** of a code intelligence benchmark. For each of the 6 cases you will use **only GitNexus MCP tools** to answer the same questions that were previously answered with grep.

**Do not use grep, find, or file reads to answer the questions.** Use MCP tools exclusively. The goal is to see what the knowledge graph surfaces that grep missed, and vice versa — including cases where they are equivalent.

If any tool warns the index is stale, run `npx gitnexus analyze` in terminal first.

## Output format

```ts
with: {
  approach: "e.g. gitnexus_context({name: \"AppShell\"})",
  steps: [
    { type: "command", content: "gitnexus_context({name: \"AppShell\"})" },
  ],
  outputExcerpt: `paste the most relevant excerpt from the MCP response (~10 lines max)`,
  coverage: 95,           // honest estimate: % of true answer the tool surfaced
  stepsCount: 1,          // number of MCP calls made
  estimatedMinutes: 0.2,  // use decimals — MCP calls are fast
  missedItems: [],        // anything the graph didn't surface
},
verdict: "One sentence: what the graph found that grep missed, or where they were equivalent.",
```

**On verdicts for ties:** Case 04 (layout-primitives consumers) is expected to be close to a tie — grep handles package.json scanning well. Write honest verdicts, including when the advantage is small.

## The 6 Cases

---

### Case 01 — Symbol callers
**Query:** "What components call AppShell?"

Use: `gitnexus_context({name: "AppShell"})`

If there are multiple `AppShell` symbols (shared vs. local), run it for each and note the distinction.

Record:
- All callers returned (direct and indirect)
- Execution flows `AppShell` participates in
- Anything the grep session missed
- Whether the graph distinguishes the shared vs. local AppShell correctly

---

### Case 02 — Blast radius
**Query:** "What breaks if I change the shared design tokens?"

Use:
1. `gitnexus_impact({target: "baseTailwindConfig", direction: "downstream"})`
2. Also try `gitnexus_impact({target: "tokens", direction: "downstream"})` for the CSS side

Record:
- Full downstream impact list with depth and confidence levels
- Depth-1 (direct) vs depth-2+ (transitive) consumers
- Risk level returned (LOW / MEDIUM / HIGH / CRITICAL)
- Anything the grep session found that the graph missed, or vice versa
- Whether the graph surfaces the MCP server as a consumer of design-tokens (it is one)

---

### Case 03 — Execution trace
**Query:** "Trace the full path from user clicking Play to the canvas rendering a new frame"

Use:
1. `gitnexus_query({query: "user clicks play canvas render island algorithms visualizer"})` to find the relevant process
2. Read the process resource: `gitnexus://repo/proto-portal-showcase-hub/processes` to see all named flows
3. Follow with `gitnexus_context({name: "usePlayback"})` and `gitnexus_context({name: "VisualizerCanvas"})` as needed

Record:
- The full execution flow as returned by the graph
- Steps/nodes the manual file-read trace missed
- Whether the graph surfaces the Three.js render call chain (CellInstances, Scene2D/Scene3D)
- Total MCP calls required vs. file reads in the pre session

---

### Case 04 — Package consumers
**Query:** "Which prototypes and apps import `@proto-portal/layout-primitives`?"

Use: `gitnexus_cypher({query: "MATCH (f:File)-[:IMPORTS]->(t:File) WHERE t.path CONTAINS 'layout-primitives' RETURN DISTINCT f.path ORDER BY f.path"})`

Also try: `gitnexus_context({name: "AppShell"})` on the shared layout-primitives AppShell to see its consumer list.

Record:
- Complete list of consumers returned
- Whether this matches grep's result (expected near-tie)
- Note if the graph adds any insight (e.g. which specific symbols from layout-primitives each consumer uses)

---

### Case 05 — Safe rename
**Query:** "If I rename `useVisualizerStore`, what files would change?"

Use: `gitnexus_rename({symbol_name: "useVisualizerStore", new_name: "useIslandStore", dry_run: true})`

Record:
- Every file the rename tool identifies
- Confidence tags on each edit (graph-confirmed vs. ast_search)
- Whether the list matches or exceeds what grep found
- Any dynamic references or string usages flagged

---

### Case 06 — API key trace
**Query:** "Trace the Claude API key from its environment variable to the actual HTTP request"

Use:
1. `gitnexus_query({query: "Claude API key ANTHROPIC_API_KEY environment variable HTTP request"})` 
2. Follow with `gitnexus_context` on the key symbols in the returned chain

Record:
- Full chain from env var to the Anthropic SDK call
- Files and functions in the execution flow
- Whether the graph surfaces both the local dev path (`.env`) and the production path (Lambda/Secrets Manager)
- Anything the grep session couldn't determine
